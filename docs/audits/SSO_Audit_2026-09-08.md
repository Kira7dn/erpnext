# Letron SSO audit — 2026-09-08

## Phạm vi và kết luận

Audit tập trung vào mục tiêu Global Portal là nguồn session/authorization duy nhất, giảm độ trễ, loại bỏ gọi Lark trùng và dọn logic legacy. Không đọc hoặc ghi secret. Sau remediation, ERPNext chỉ nhận signed Gateway claims; session lookup không gọi Lark và role projection có lock.

## Findings

### SSO-001 — High: flow native ERPNext/OIDC legacy (fixed)

- Location: `apps/letron_api/letron_api/sso.py:136-246`, `apps/letron_api/letron_api/sso_protocol.py:10-190`.
- Evidence: `launch()` và `callback()` vẫn là `@frappe.whitelist(allow_guest=True)`; `sso_protocol.py` vẫn định nghĩa `CALLBACK_PATH`, `LAUNCH_PATH`, OIDC code exchange, nonce và role sync.
- Impact: có hai chủ sở hữu login/session/identity (`letron_api.sso` và Global Portal). Logic này tăng chi phí bảo trì, có thể bị mở lại khi route/exemption thay đổi và làm acceptance không xác định đang kiểm tra flow nào.
- Fix: đã xoá `sso.py`, xoá OIDC code-exchange/callback contract khỏi `sso_protocol.py`, catalog và script provision client; native `/api/resource` và `/api/method` tiếp tục bị chặn bởi ingress.

### SSO-002 — High: Lark group sync bị gọi trùng trên cùng flow (fixed)

- Location: `apps/auth-server/pages/api/auth/lark/callback.ts:46`, `apps/auth-server/pages/api/auth/lark/start.ts:52-55`, `apps/auth-server/src/server/session.ts:80-114`, `apps/auth-server/src/server/users.ts:66-78`.
- Evidence: callback gọi `fetchLarkGroupIds`; `getUserBySessionToken()` cũng refresh stale identity; `start.ts` gọi `getUserBySessionToken()` rồi tiếp tục gọi `refreshLarkGroupsForUser()` cho user hiện hữu; helper `refreshLarkGroupsForUser()` tự gọi Lark mà không dùng cùng lease.
- Impact: tăng latency login/session, tạo nhiều tenant-token/group requests, và cạnh tranh DB/Lark khi nhiều request song song.
- Fix: đã tạo `syncLarkGroupsIfStale(userId)` dùng lease/đợi snapshot; Gateway là coordinator duy nhất cho request; session lookup và start continuation không refresh lần hai.
- Mitigation: giữ TTL snapshot và lock theo identity; đo số request Lark/user/login trong test concurrency.
- False positive notes: một số call có thể xảy ra ở request khác nhau, nhưng hiện không có shared coordinator để chứng minh chúng không trùng.

### SSO-003 — High: session lookup vẫn phụ thuộc synchronous Lark network (fixed)

- Location: `apps/auth-server/src/server/session.ts:80-114`.
- Evidence: khi `groupsSyncedAt` stale, `getUserBySessionToken()` lấy lease, chờ tối đa 2 giây, gọi `fetchLarkGroupIds()`, và trả `null` khi refresh/lease không hoàn tất.
- Impact: các endpoint đọc session (`/api/auth/session`, Gateway, page render) có thể tăng latency hoặc biến lỗi mạng/lock contention thành logout/login failure. Đây là regression trực tiếp với mục tiêu giảm độ trễ.
- Fix: đã tách session validity khỏi refresh. Gateway trả `503 access_policy_unavailable` khi coordinator không xác nhận được policy; không biến lỗi Lark/lock thành logout giả.
- Mitigation: bounded stale-while-revalidate chỉ khi policy contract cho phép; khi policy hết hạn thì trả lỗi authorization có mã rõ ràng, không giả dạng unauthenticated.
- False positive notes: fail-closed có thể là lựa chọn bảo mật hợp lệ, nhưng vẫn cần trả trạng thái `503 policy unavailable` thay vì `401`/login failure nếu chỉ là dependency outage.

### SSO-004 — Medium: role projection chưa có lock riêng ở ERP (fixed)

- Location: `apps/letron_api/letron_api/gateway.py:82-116`.
- Evidence: `sync_gateway_roles_if_changed()` đọc fingerprint, có thể `User.save(ignore_permissions=True)`, sau đó `set_value()` identity; không có lock theo identity/user quanh toàn bộ read-modify-write.
- Impact: hai Gateway request cùng fingerprint mới có thể cùng sửa User/commit, gây deadlock hoặc ghi đè trạng thái; đúng failure mode mà distributed lock đang cần loại bỏ.
- Fix: đã thêm Redis/Frappe cache lock theo identity bao quanh fingerprint read-modify-write; không `User.save()` khi fingerprint/policy version không đổi.
- Mitigation: retry hữu hạn cho deadlock và metric lock wait/role sync duration.
- False positive notes: Frappe DB có thể serialize một phần thao tác, nhưng không thay thế lock application-level cho read-modify-write.

### SSO-005 — Medium: callback origin được suy ra từ forwarded host ở hai nơi (fixed)

- Location: `apps/auth-server/pages/api/auth/lark/start.ts:28-36`, `apps/auth-server/pages/api/auth/lark/callback.ts:40-43`.
- Evidence: `start.ts` có allowlist host riêng; `callback.ts` lấy `x-forwarded-host`/`host` và dựng `https://host` mà không dùng cùng allowlist.
- Impact: origin/config drift tạo Lark error `20029`; khác biệt proxy header có thể làm start và callback dùng URI khác nhau. Đây là nguyên nhân của incident redirect vừa xảy ra.
- Fix: đã centralize `canonicalAuthOrigin(req)`; chỉ cho localhost hoặc host của `AUTH_BASE_URL`, host proxy lạ quay về canonical origin. Start và callback dùng cùng helper.
- Mitigation: audit log request ID + canonical origin (không log token), test qua localhost, custom domain và Vercel hostname.
- False positive notes: reverse proxy có thể bảo đảm header; điều đó chưa được chứng minh trong app code.

### SSO-006 — Medium: native ingress có public exemptions cần contract rõ (fixed)

- Location: `apps/letron_api/letron_api/gateway.py:118-132`, `apps/letron_api/letron_api/access_policy.py:52-62`, `apps/letron_api/letron_api/api.py:21-54`.
- Evidence: `/api/method/letron_api.access_policy.publish` được miễn native block; method có `allow_guest=True` nhưng dùng `X-Letron-Policy-Secret`. health/runtime cũng là guest-capable/exempt paths.
- Impact: policy publication và metadata endpoints không đi qua signed Global Portal claims. Secret header là một authorization contract riêng, làm hệ thống không hoàn toàn “Gateway-only” và tăng surface/duplicate auth model.
- Fix: policy publish đã chuyển sang control-plane HMAC có timestamp/expiry/request ID riêng; bỏ `X-Letron-Policy-Secret` đơn giản. Native business APIs vẫn bị ingress chặn; health/runtime chỉ còn read-only operational endpoints.
- Mitigation: control-plane signature kiểm tra exact HMAC, timestamp/expiry/request ID; cần bổ sung rate limit/network restriction ở hạ tầng nếu endpoint được expose ra ngoài private ERP origin.
- False positive notes: `publish()` vẫn tự kiểm tra secret; finding là duplicate trust boundary, không khẳng định endpoint đang unauthenticated.

### SSO-007 — Low: client/server auth origin fallback phân tán (fixed)

- Location: `apps/erp/src/proxy.ts:7`, `apps/erp/src/lib/portal-session.ts:12`, `apps/erp/src/lib/letron-api.ts:127`, `apps/erp/src/app/api/auth/login/route.ts:4`.
- Evidence: nhiều module tự đọc `LETRON_AUTH_BASE_URL` với fallback riêng.
- Impact: một biến môi trường sai có thể làm proxy, session lookup, API Gateway và logout trỏ tới các origin khác nhau; khó debug và gây request vòng/latency.
- Fix: đã gom origin vào `apps/erp/src/lib/portal-config.ts`; proxy, session, API routes và logout dùng cùng helper.
- Mitigation: startup validation và runtime health kiểm tra origin consistency.

## Verification evidence

- Auth Server `npm run check`: pass.
- Browser local: ERP → Auth → Lark page, callback URI local.
- Browser production: Auth → Lark page, callback URI `auth.letron.vn`.
- Production health: `200`, group sync enabled, no stale identity reported at audit time.
- Chưa xác minh callback thành công bằng user authorization code thật; chưa chạy soak đo đồng thời Lark request count/deadlock. Đây là external/runtime acceptance, tách biệt với static/browser pre-auth checks.

## Cập nhật frontend và PWA

Sau audit, ERP Next.js đã hoàn tất client data layer bằng TanStack Query và giữ
nguyên Global Portal là nguồn session/authorization. Các mutation client đã có
resource invalidation; không còn `fetch` trực tiếp trong component client.

PWA nhẹ đã được thêm nhưng không tạo thêm nguồn session hoặc cache business
data. Accounting và Assets có manifest riêng với scope tương ứng; manifest và
icon được public qua route metadata không yêu cầu session. Không triển khai
service worker/offline cache.

Các kiểm tra frontend hiện tại: typecheck, lint, build và production manifest
HTTP 200 đều pass. Browser/device install acceptance và kiểm chứng đầy đủ flow
Lark → Auth → ERP vẫn là runtime gate riêng, chưa được suy ra từ build hoặc
HTTP 200.

## Recommended implementation order

1. SSO-002 và SSO-003: một coordinator sync, loại bỏ native implementation.
2. SSO-003 và SSO-004: tách session lookup khỏi network Lark, canonical origin duy nhất.
3. SSO-004: lock role projection ở ERP.
4. SSO-006 và SSO-007: gom control-plane auth/config và thêm contract tests.
5. Frontend runtime: kiểm tra install PWA riêng cho Accounting/Assets và đo
   navigation trong Lark; không dùng PWA để thay thế SSO/Gateway acceptance.
